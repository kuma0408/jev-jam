# 0006. 次に選べるコードすべての分のソロを、選ばれる前に作っておく

- 日付: 2026-10-13
- ステータス: Accepted
- 種別: 設計判断

## 背景

ユーザーは再生中の小節のあいだに次のコードを選ぶ。選んだコードの小節が始まる時点で、
そのコードに合うソロが用意できていなければならない。
実測（0005）で、Jevは1小節ぶんを170〜340msで返すと分かっている。

## 検討した選択肢

- 案A: 小節の頭で、次に選べる候補すべての分を並列に依頼する。小節の最後まで選べて、選んだ瞬間に遅延が無い。呼び出しは候補数倍になる
- 案B: 4拍目の頭で選択を締め切り、決まったコードの分だけ依頼する。呼び出しは最小だが、選べる時間が短く、速いテンポで間に合わない恐れがある
- 案C: 選択を2小節先に反映する。確実に間に合うが、押してから音が変わるまでが遠く、セッション感が薄れる

## 決定

案A。公式ドキュメントの「Speculative Fan-Out」パターンにあたる。
候補は2〜5個で、使わなかった分は捨てる。Jevの料金（入力 $0.042/100万トークン、出力無料）なら無駄は無視できる。

実装では、候補ごとに別のリクエストを並列に投げている。
1リクエストに全候補の質問を詰める形にしなかったのは、`state` に「今のコード」を1つしか書けないため。

## 結果

確認用の画面（`pnpm dev`）で動かし、90BPMで次の点を確かめた。

- 候補4〜5個ぶんの準備が、小節の頭から220〜380msで終わる（1小節は約2670ms）
- 選ばなければ既定の候補に自動で進み、選べばそのコードのソロに切り替わる

捨てる分も含めると、1小節あたり2〜5回、2段階方式なら4〜10回Jevを呼ぶ。
公開時にレート制限（1,200リクエスト/分）や費用の面で問題にならないかは、同時利用者数が決まってから見直す。
