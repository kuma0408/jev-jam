# 0004. アプリ本体より先に、Jevの検証スパイクから始める

- 日付: 2026-10-13
- ステータス: Accepted
- 種別: 設計判断

## 背景

このアプリの成否は「Jevの判断で、聞いて気持ちいいソロが間に合う速度で作れるか」にかかっている。
これは机上では決められない。一方、着手時点でJevのAPIキーはまだ無い。

## 検討した選択肢

- 案A: Jevの検証スクリプトから始める。最大の不確実性を先に潰せる
- 案B: コード進行エンジンから始める。Jevに依存せず進むが、肝心のソロの成否が後回しになる
- 案C: 音が鳴る最小UIから始める。見た目の進捗は早いが、Jevが期待外れなら手戻りが大きい

## 決定

案A。キーが届くまでは、Jevと同じ形の応答を返すダミーを相手に組み立て、
キーが届いたら差し替えるだけで実測できる状態にしておく。

## 結果

2026-10-13にダミー相手の配線を終え、同日に本物のJevで実測した（結果は0005）。

- `pnpm spike` で、一括方式と2段階方式を同じ進行（Dm7 G7 Cmaj7 A7）で走らせられる
- 出力は、小節ごとの遅延、選ばれた音、MIDIファイル（`spikes/out/`）
- `.env` に `TYPESAFE_API_KEY` を書けば本物のJevに切り替わる

未確認の前提が2つある。どちらも初回の実呼び出しで確かめる。

- リクエストとレスポンスの形は公式クイックスタートの要約と二次情報から組んだ。
  特に `probabilities` が「ラベル → 確率」のオブジェクトであることは未確認（違えば生の応答を表示して止まる）
- ダミーの確率はでたらめなので、音楽的な質と2方式の差はまだ何も分かっていない

計測する項目は0001の「結果」を参照。
